# 과학 포트리스: 힘과 운동 미션

**발사 각도·힘·탄환을 조절해 목표물을 맞히며 배우는 중학교 과학 교육용 2D 포트리스 게임.**

학생은 중력·마찰·공기 저항·바람이 물체의 운동을 어떻게 바꾸는지를 공식이 아니라
직접 조작과 예측으로 체득한다. 실패한 궤적을 보고 조건을 하나씩 바꿔 다시 도전하는
"변인 통제"가 게임의 핵심 루프다.

## 바로 플레이

**▶ https://biiinsb.github.io/science-fortress/**

## 실행

빌드 도구도, 설치도, 서버도 필요 없다. `index.html`을 브라우저로 열면 끝이다.
외부 폰트·CDN·오디오 파일을 하나도 부르지 않아 학교 오프라인망에서도 그대로 돈다.
저장소를 내려받아 파일을 열기만 해도 되므로, 인터넷이 막힌 교실에서도 쓸 수 있다.

## 게임 모드 (PRD 5, PDF p.9)

- **스테이지 모드** — 5개 맵을 순서대로 클리어하고 총점을 랭킹에 등록한다.
- **연습 모드** — 점수 없이 무제한 발사. 전체 예측선을 켤 수 있는 개념 탐색용.
- **챌린지 모드** — 바람·마찰·공기 저항이 랜덤·복합으로 작용한다. 최고 기록 도전.
- **교사용 시연** — 교사가 조건을 강제한다. 같은 각도·힘으로 바람·마찰만 바꿔
  비교 발사하며, 지난 궤적이 함께 남는다.

## 조작

- **대포를 뒤로 끌어당겼다 놓으면** 발사된다 (포트리스식 슬링샷). 당긴 **방향**의
  반대가 발사 각도를, 당긴 **길이**가 발사 힘을 정한다. 각도·힘은 대포 옆에 숫자로 뜬다.
- 키보드로도 조작된다: **↑↓** 각도, **←→** 힘, **스페이스** 발사. (슬라이더는 "정밀 조절"에 접혀 있다.)
- **탄환 2종** — 둥근(ROUND)·무거운(HEAVY). 둘은 **모양(항력)이 같고 질량만 다르다.**
  탄환만 바꿔 보면 질량의 효과를 변인 통제로 관찰할 수 있다: 무거운 탄환은 같은 힘에
  덜 나가지만, 그 대신 바람과 공기 저항에 덜 흔들린다.
- **목표물은 기둥 위에 떠 있어** 굴려서는 닿지 못한다. 반드시 포물선으로 띄워 넣어야 한다.
- **맵을 다시 시작할 때마다 목표물 거리와 바람이 바뀐다.** 화면 왼쪽 위의 바람(방향
  화살표 + 풍속 1~5)을 확인하고 매번 새로 조준해야 한다.

## 맵 (PRD 7)

| 맵 | 이름 | 켜지는 변인 | 핵심 개념 |
| :--- | :--- | :--- | :--- |
| Map 1 | 훈련 평원 | (없음) | 힘의 크기와 방향 |
| Map 2 | 모래 협곡 | 지면 마찰 (얼음·흙·모래) | 마찰력 |
| Map 3 | 바람 절벽 | 바람 | 바람에 의한 경로 변화 |
| Map 4 | 저항의 숲 | 공기 저항 + 장애물 | 공기 저항과 물체 질량 |
| Map 5 | 최종 요새 | 마찰·바람·저항·방어벽 | 종합 적용 |

난이도(Level 1~5)는 맵과 **직교**한다. 맵이 *어떤* 변인을 켤지 정하고, 난이도는 그
변인이 *얼마나 세게* 작용하고 발사 횟수를 얼마나 줄지 정한다. (PRD가 Level과 Map을
이중 정의한 충돌을 이렇게 풀었다 — [개발 계획서 0.1(1)](science_fortress_dev_plan.md) 참고.)

## 교육과정 범위 (PRD 2.3)

학생 화면에는 포물선 공식·삼각함수·벡터 분해·가속도 방정식·속도 벡터·성분을 **표시하지
않는다.** 내부 물리 엔진은 정확히 계산하되, 학생에게는 "발사 힘이 클수록 더 멀리 날아간다",
"공기 저항이 크면 속력이 더 빨리 줄어든다" 같은 중학교 수준의 말로만 제시한다. 화면에
나가는 문자열은 전부 `feedback.js` 한 곳에 모아 두어, 금지 범위를 넘지 않았는지 한눈에
검토할 수 있다.

### 왜 게임 프레임워크(Phaser·Matter.js)를 안 쓰나

필요한 물리는 질점 + 중력 + 선형 항력 + 바람 + 지면 구름 마찰이 전부다. 자체 고정 스텝
적분기가 **결정론을 설계로 보장**하고 — 같은 입력은 반드시 같은 궤적을 낳는다 — 이 성질이
변인 통제(같은 조건 재현)와 실패 진단의 토대다. 실패 진단은 같은 발사를 조건만 바꿔 수십
번 다시 굴리는데(반사실 시뮬레이션), 순수 함수면 그냥 다시 호출하면 된다. 자세한 근거는
[개발 계획서 4.2](science_fortress_dev_plan.md)에 있다.

## 실패 원인 진단

"힘이 약해서"인지 "공기 저항 때문에"인지는 착탄점 하나로는 알 수 없다 — 둘 다 "짧게
떨어짐"으로 나타난다. 그래서 각 환경 변인을 하나씩 끈 **반사실을 끝까지 다시 굴려**, 그
변인을 제거했다면 목표에 명중권까지 가까워졌을 때만 그것을 원인으로 지목한다. 여러 변인이
비슷하게 작용해 애매하면 변인을 지목하지 않고 "힘을 조금 키워 보세요" 같은 일반 조언으로
후퇴한다. **틀린 과학 설명을 하느니 두루뭉술한 게 낫다.**

## 테스트

Node 없이 브라우저 하나로 순수 로직을 검증한다.

```powershell
py tools/run.py tests/physics.test.html   # 물리 코어 (단언 61)
py tools/run.py tests/logic.test.html     # 점수·진단 (단언 42)
py tools/run.py tests/smoke.test.html     # 실제 앱 구동 (단언 16)
py tools/run.py tools/calibrate.html      # 25조합(5맵×5난이도) 클리어 가능성 실증
```

브라우저에서 각 `tests/*.html`을 직접 열어도 결과가 화면에 표시된다.

`tools/calibrate.html`은 테스트가 아니라 **맵 밸런싱 도구**다. 맵 좌표나 물리 상수를 바꿀
때마다 25조합이 여전히 전부 클리어 가능한지 실측한다. 이 관문이 초기 맵 설계에서 Map 5가
클리어 불가였음을 잡아냈다.

## 전체 공유 랭킹 (선택, 무료)

기본은 **이 기기에만** 저장되는 로컬 랭킹이다(localStorage). 접속한 모두가 같은
명예의 전당을 보게 하려면 [`firebase-config.js`](firebase-config.js)에 무료 Firebase
**Realtime Database** 주소(`databaseURL`) 하나만 채우면 된다 — 파일 안에 단계별
안내가 있다. 설정 전까지는 게임이 그대로 돌아가되 랭킹만 기기별로 저장된다.
`cloud.js`가 설정 유무를 보고 자동으로 전환한다.

Firestore가 아니라 Realtime Database를 쓰는 이유: Firestore는 최근 결제 계정을
요구하는 경우가 있지만 RTDB는 무료로 결제 없이 된다. 게다가 REST(주소로 GET/POST)라
**SDK도 외부 CDN도 부르지 않는다** — 외부 스크립트 0개 원칙을 공유 랭킹에서도 지킨다.
게임 본체는 여전히 오프라인망에서 돌아가고, 오프라인일 때는 로컬 랭킹으로 되돌아간다.

## 개인정보 보호 (PRD 11.5)

실명·연락처를 요구하지 않는다. 랭킹에는 닉네임만 저장하고, 위험 문자는 제거한다.
로컬 모드에서는 데이터가 브라우저에만 남는다. 공유 랭킹을 켜면 닉네임·점수·난이도·
날짜만 Realtime Database에 저장되며(개인 식별 정보 없음), 데이터베이스 규칙이 남의
기록을 고치거나 지우지 못하게 막는다.
